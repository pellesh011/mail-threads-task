## Как запустить

```
cp .env.example .env    # вписать свой CANDIDATE
docker compose up --build worker    # импорт всей ленты + сборка разговоров, завершается кодом 0
docker compose run --rm exporter    # читает базу и пишет ./out/result.jsonl
node selfcheck.js out/result.jsonl # локальная самопроверка (необязательно)
```

`docker compose up worker` сам поднимает зависимости (provider, db, redis). Миграции применяются автоматически при старте внутри worker.

## Как устроено хранение и почему

`RawMessage` — сырые письма как пришли от провайдера, источник истины ленты: их храним отдельно, чтобы можно было пересобрать разговоры без повторной выгрузки. Из них `BuildThreadsUseCase` создаёт `Message`. Внешние идентификаторы лежат в `MessageReference` с unique по `(providerId, externalId)` — так повторно пришедшее от провайдера письмо не дублируется. Рёбра `references` хранятся в `MessageToMessageReference` (с порядком) — по ним вместе с `in_reply_to` строится граф разговоров. `Thread` — разговор. `Task` — очередь задач импорта по курсорам и единственная задача сборки, что и даёт продолжение с места остановки. `Provider` — сущность источника писем.

## Если появится второй почтовый сервис

Необходимо будет добавить обработчик вебкуха в represetnation, в infrastructure добавить обработчик нового провайдера, для записи сырых данных в бд, создать usecase для перевода полученных данных соответствующей нашей структуре хранения данных. Доменные сущности и бд изменять не нужно, Записи в таблицах MessageReference и ThreadReference не обяхательны (можно самому генерировать, если необходимо), а остальные таблицы вообще не требуют внешних идентификаторов, они работают на собственных сгенерированных UUID.

## Что произойдёт при одновременном запуске двух сервисов над одной базой

Если запустить и expoter (читает только таблицу Message) и worker, worker'у это не помешает, а вот экспортёр не получит необходимых данных для экспорта. На этапе полученя данных от провайдера, данных в результате не будет вообще, а на этапе построения threads, данные будут неполные, thread_key может быть либо пустым, либо не полным, как и parent_id.

## Есть ли шаг, который нельзя выполнить дважды без последствий

Такого шага нет — весь конвейер идемпотентен. Повторный импорт не создаёт дублей за счёт unique `(providerId, externalId)` и unique `(providerId, cursor)`, повторная сборка разговоров пересчитывает рёбра (delete + insert), переиспользует существующие `Thread` и удаляет только осиротевшие, а миграции применяются через идемпотентный `migrate deploy`. Повторный запуск уже завершённого worker просто сразу выходит: задач в статусе PENDING нет.

## Что вы решили не усложнять

Не выносили отдельный слой абстракции под несколько провайдеров: коннектор жёстко завязан на один API постраничной ленты. Станет оправданно, когда появится второй источник — тогда протокол выделим в интерфейс.

## Что перестанет работать при десятикратном объёме писем

Первым упрётся сборка разговоров: `BuildThreadsUseCase` читает всю ленту в память.
